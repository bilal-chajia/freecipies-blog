# Site Settings Table Contract

This document is the product/data contract for the `site_settings` table. The executable SQL source remains `db/schema.sql`.

## Scope

`site_settings` is a key-value registry for global CMS/site configuration. It is used for settings that do not justify a dedicated relational table.

Current code uses it for:

- image upload settings
- table-of-contents appearance settings
- menu configuration through the menus module
- AI/provider settings migration paths
- future branding, SEO, social, analytics, and theme groups

Related contracts:

- `docs/MEDIA_TABLE_CONTRACT.md` for image upload behavior affected by settings
- `docs/DATABASE_CONTENT_MODEL.md` for table ownership overview
- `src/modules/settings/services/settings.service.ts` for current merge-with-defaults behavior
- `src/modules/menus/services/menus.service.ts` for menu storage behavior

## Source Of Truth

`site_settings.key` is the stable identity of a setting.

`site_settings.value` stores the setting payload as text. The application parses and validates it according to `type` and the known schema for that key.

The table is not a public config API by itself. The current SQL schema does not include an `is_public` column, so public exposure must be decided by the service/API that reads the setting.

## Columns

| Column | Required | Owner | Contract |
| --- | --- | --- | --- |
| `key` | yes | App/Admin | Primary key. Stable lowercase `snake_case` identifier. |
| `value` | yes | App/Admin | Text payload. Usually JSON string for structured settings. |
| `description` | no | Admin/UI | Helper text for admin settings screens. |
| `category` | no | Admin/UI | Admin grouping, default `general`. |
| `sort_order` | no | Admin/UI | Display order inside a category. |
| `type` | no | Admin/UI/App | Editor/parsing hint. Default `json`. |
| `updated_at` | no | DB | Updated by SQL trigger. |

Supported `type` values in `db/schema.sql`:

- `json`
- `text`
- `number`
- `boolean`
- `image`
- `color`
- `code`

## Value Contract

`value` is always stored as TEXT.

Parsing rules:

- `type = json`: `value` must be valid JSON and parse to the schema expected by `key`.
- `type = text`: `value` is a plain string.
- `type = number`: `value` is a stringified number and must parse safely.
- `type = boolean`: use stringified boolean JSON (`true` / `false`) or a controlled app-level representation.
- `type = image`: `value` should store a stable image reference, preferably a `media_id` or image-slot object, not a hardcoded absolute domain URL.
- `type = color`: `value` should be a validated CSS color token or hex value.
- `type = code`: only for trusted admin-managed snippets; never execute unsanitized code in admin or public rendering.

## Key Naming

Rules:

- Use lowercase `snake_case`.
- Keys must be stable because services reference them directly.
- Prefer namespaced keys when a feature owns a group:
  - `image_upload_settings`
  - `toc_settings`
  - `menu_header`
  - `menu_footer`
  - `ai_settings`
  - `seo_defaults`
  - `social_links`

Avoid:

- UI labels as keys.
- Mixed case keys.
- Keys containing tenant/domain names unless multi-tenant scoping is explicitly designed.

## Known Setting Shapes

### Image Upload Settings

Source: `src/shared/constants/image-upload` and `src/modules/settings/services/settings.service.ts`.

The service reads the stored partial object and merges it over `IMAGE_UPLOAD_DEFAULTS`.

Rules:

- Store only overrides or the full normalized settings object.
- Validation belongs to the settings API/service.
- Upload endpoints must read the merged settings, not raw `site_settings.value`.

### TOC Settings

Current key: `toc_settings`.

```json
{
  "enabled": true,
  "numbering": true,
  "collapsible": true,
  "defaultOpen": true,
  "showJumpButton": true,
  "accentColor": "#f97316",
  "maxDepth": 4
}
```

Current code uses camelCase keys here. Do not silently rename this stored shape during the contract phase. If a future refactor standardizes settings JSON to `snake_case`, migrate this key intentionally.

### Menu Settings

Current menu keys are generated by the menus service, for example:

- `menu_header`
- `menu_footer`
- `menu_mobile`
- `menu_sidebar`

Stored value shape:

```json
[
  {
    "id": "recipes",
    "label": "Recipes",
    "href": "/recipes",
    "children": []
  }
]
```

Rules:

- Menus are configuration, not article content.
- Missing/empty menu settings fall back to service defaults.
- Deleting a menu currently stores an empty array rather than deleting the setting row.

## Runtime Usage

Admin:

- Settings screens group rows by `category` and order by `sort_order`.
- Feature-specific settings APIs should validate the payload for their own key.

Public Astro/API:

- Public pages should read only explicit, safe settings needed for rendering.
- Do not expose all settings wholesale.
- Do not expose secrets or provider API keys from this table.

## Security Rules

- Prefer Cloudflare secrets for real secrets such as API keys.
- If a sensitive value is temporarily stored in `site_settings`, never expose it through public APIs.
- `code` settings require strict trust boundaries and sanitization.
- `image` settings should avoid hardcoded absolute URLs when a `media_id` or R2 key can be resolved dynamically.

## Validation Rules

- `key`: required, unique, lowercase `snake_case`.
- `value`: required text.
- `category`: default `general`.
- `sort_order`: integer, lower appears first.
- `type`: one of the SQL-supported values.
- JSON payloads must be validated by the feature service before save.

## Lifecycle Rules

- No `created_at` column exists in the current SQL schema.
- No `deleted_at` soft delete exists for this table.
- Removing a setting is a hard delete, except feature services may choose to reset to defaults or store an empty value.
- `updated_at` is maintained by SQL trigger.

## Known Implementation Notes

- `src/modules/settings/schema/settings.schema.ts` currently matches the active SQL columns: `key`, `value`, `description`, `category`, `sort_order`, `type`, and `updated_at`.
- There is no current SQL `is_public` flag. If public/private settings become necessary, add it deliberately to SQL, Drizzle, docs, and APIs together.
