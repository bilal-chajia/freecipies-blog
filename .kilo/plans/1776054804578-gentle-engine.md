# Plan: Store R2 Keys Only & Build Image URLs Dynamically

## Problem

Absolute/proxy URLs (e.g., `/api/images/media/brown-butter-...webp`) are stored directly in database JSON columns (`media.variants_json`, `articles.images_json`, `categories.images_json`, `authors.images_json`, `equipment.image_json`, `articles.content_json`). When the domain or proxy path changes, all stored URLs become invalid or require migration.

## Goal

Store **only R2 keys** in all database JSON fields. Build image URLs dynamically at read/render time using a centralized function. This eliminates the need for URL migrations and ensures URLs are always correct.

---

## Phase 1: Type System & Core Function

### 1.1 New stored variant type (`src/shared/types/images.ts`)

Add a `StoredImageVariant` type (no `url`, only `r2_key`):

```typescript
export interface StoredImageVariant {
  r2_key: string;
  width: number;
  height: number;
  sizeBytes?: number;
}

export interface StoredImageVariants {
  xs?: StoredImageVariant;
  sm?: StoredImageVariant;
  md?: StoredImageVariant;
  lg?: StoredImageVariant;
  original?: StoredImageVariant;
}
```

### 1.2 Centralized URL builder (`src/shared/types/images.ts`)

Add a `buildImageUrl()` function:

```typescript
const IMAGE_PROXY_PREFIX = '/api/images';

export function buildImageUrl(r2Key: string): string {
  return `${IMAGE_PROXY_PREFIX}/${r2Key}`;
}
```

### 1.3 Conversion functions (`src/shared/types/images.ts`)

```typescript
// Stored -> Public (adds url from r2_key)
export function storedToPublicVariant(sv: StoredImageVariant): ImageVariant {
  return { url: buildImageUrl(sv.r2_key), width: sv.width, height: sv.height, sizeBytes: sv.sizeBytes };
}

// Public -> Stored (removes url, keeps r2_key if present)
export function publicToStoredVariant(pv: ImageVariant & { r2_key?: string }): StoredImageVariant | null {
  if (!pv.r2_key) return null; // Can't convert without r2_key
  return { r2_key: pv.r2_key, width: pv.width, height: pv.height, sizeBytes: pv.sizeBytes };
}

// Recursively convert all variants
export function storedVariantsToPublic(variants: StoredImageVariants): ImageVariants
export function publicVariantsToStored(variants: ImageVariants & { [k]: { r2_key }? }): StoredImageVariants | null
```

### 1.4 Backward-compatible reader (`src/shared/types/images.ts`)

Update `resolveVariantUrl()` to handle BOTH formats:
- If `r2_key` is present → build URL dynamically via `buildImageUrl()`
- If only `url` is present → use as-is (legacy data)

```typescript
export function resolveVariantUrl(variant: { url?: string; r2_key?: string }): string | null {
  if (variant.r2_key) return buildImageUrl(variant.r2_key);
  if (variant.url) return variant.url;
  return null;
}
```

### 1.5 Update existing helper functions

Update these functions to use `resolveVariantUrl()`:
- `getBestVariantUrl()` — use `resolveVariantUrl()` instead of `variant.url`
- `getSrcSet()` — use `resolveVariantUrl()` for each variant
- `stripStorageKeys()` — now removes `url` too and converts r2_key → url
- `rewriteR2UrlToProxy()` — no longer needed long-term, keep for migration period

## Phase 7: Migration Script

### 7.1 Create migration script (`scripts/migrate-r2-keys-only.js`)

This script will:

1. **`media` table:** For each row, parse `variants_json`, replace `url` fields with nothing (keep `r2_key`), write back
2. **`articles` table:** Parse `images_json`, for each variant that has `url` but no `r2_key`, derive `r2_key` from URL pattern `/api/images/{r2_key}`, replace `url` with `r2_key`, write back
3. **`articles.content_json`:** Parse content blocks, find image blocks with `variants`, apply same transformation
4. **`categories` table:** Same transformation on `images_json`
5. **`authors` table:** Same transformation on `images_json`
6. **`equipment` table:** Same transformation on `image_json`
7. **`articles.cached_*_json`:** These contain extracted URLs — either rebuild them from source data or transform inline

**URL → r2_key extraction:**

```javascript
function extractR2KeyFromUrl(url) {
  if (!url) return null;
  // /api/images/media/foo.webp -> media/foo.webp
  const proxyMatch = url.match(/^\/api\/images\/(.+)$/);
  if (proxyMatch) return proxyMatch[1];
  // https://pub-xxx.r2.dev/media/foo.webp -> media/foo.webp
  const r2Match = url.match(/^https:\/\/pub-[a-f0-9]+\.r2\.dev\/(.+)$/i);
  if (r2Match) return r2Match[1];
  // http://localhost:PORT/api/images/media/foo.webp -> media/foo.webp
  const localMatch = url.match(/^https?:\/\/[^\/]+\/api\/images\/(.+)$/);
  if (localMatch) return localMatch[1];
  return null;
}
```

**Key principle:** The backward-compatible `resolveVariantUrl()` (reads both `r2_key` and legacy `url`) ensures the site keeps working during the entire migration. Old data with `url` still works; new data with only `r2_key` also works. The migration script converts old data, then cleanup removes the legacy codepath.

---

## Risk Mitigation

1. **Backward compatibility first:** `resolveVariantUrl()` handles both formats, so deployment and migration can happen independently
2. **Migration script is idempotent:** Running it multiple times produces the same result
3. **Admin panel:** API responses still include `url` (built dynamically from `r2_key`) so the admin UI works unchanged
4. **Build verification:** Run `pnpm build` after each phase to catch type errors
